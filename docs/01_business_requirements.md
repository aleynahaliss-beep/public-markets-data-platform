## 1. Purpose and context

A public-markets data team sits between the people who trade and the people who control risk. It
receives **reference data** (instruments, counterparties), **market data** (prices, FX rates),
**trade execution data** (front-office trades, back-office settlements) and **collateral balances**,
and has to deliver numbers that risk, operations and finance can trust: positions, market risk,
counterparty credit exposure and margin calls.

This project models that flow end to end on synthetic data. It is written as a *techno-functional*
deliverable: the business requirements, user stories and data definitions in this folder are
implemented one-to-one in PySpark/SQL code and verified by automated tests.

## 2. Business problem

| # | Problem observed in the feeds | Business impact |
|---|---|---|
| P1 | Reference data errors (invalid ISIN check digit, duplicate ISIN, missing currency, mistyped asset class) | Securities cannot be identified or valued; **every trade on that security is silently dropped or mis-valued**. |
| P2 | Market data faults (zero / negative prices, one-day price spikes, frozen prices, missing days, duplicate rows) | Phantom tail losses in VaR, wrong mark-to-market, understated volatility. |
| P3 | Trade faults (duplicates, zero quantity, settlement before trade date, mis-priced trades, unknown counterparties) | Double-counted positions, wrong exposure, regulatory reporting breaks. |
| P4 | Front-office and back-office disagree (missing instructions, quantity / amount / date differences) | Failed settlements, funding cost, operational loss. |
| P5 | Exposure and margin are computed from whatever data arrives | Wrong margin calls (too small = unsecured exposure, too large = disputes). |

## 3. Objectives and success measures

| Objective | Measure of success |
|---|---|
| O1 Only validated data reaches reconciliation and risk | 100% of rows breaching a CRITICAL rule are quarantined, none leak into outputs (`clean + quarantine = input` for every dataset). |
| O2 Every rejection is explainable | Each quarantined row carries the ids of **all** CRITICAL rules it broke. |
| O3 Data quality is measurable | A rule-level scorecard (PASS / WARN / FAIL) and a dimension roll-up are produced on every run. |
| O4 Front/back office differences are classified | Every trade lands in exactly one reconciliation category. |
| O5 Risk numbers are reproducible | Same inputs + same config => identical outputs; thresholds live in one config object. |
| O6 Requirements are verifiable | Each fault injected into the synthetic feeds is detected by exactly the expected rule (end-to-end test). |

## 5. Scope

**In scope**
- Seven feeds: instruments, counterparties, prices, FX rates, trades, settlements, collateral.
- 40 data-quality rules across completeness, validity, uniqueness, consistency, accuracy, timeliness and integrity.
- Front-office vs back-office trade reconciliation.
- Positions, historical-simulation VaR and Expected Shortfall, counterparty exposure with netting, CSA variation margin.
- Analyst-facing Spark SQL reports.

**Out of scope (deliberately)**
- Regulatory capital engines (SA-CCR, IMM, FRTB). The exposure add-on is an *illustrative* CEM-style formula, not a supervisory one.
- Derivatives pricing (all instruments are cash products: equities, bonds, ETFs).
- Initial margin, margin disputes, multi-currency collateral and eligible-collateral haircuts.
- Market holidays (calendar is weekdays only).
- Real vendor connectivity; feeds are CSV files.

## 6. Definitions

| Term | Meaning in this project |
|---|---|
| **Quarantine** | Table of rows that broke a CRITICAL rule, with the rule ids that caught them. |
| **MtM** | Mark-to-market of an open trade in USD: `sign x qty x multiplier x (latest price - trade price)`; positive = counterparty owes us. |
| **Netting set** | All open trades with one counterparty (assumes a master netting agreement). |
| **Replacement cost (RC)** | `max(net MtM, 0)` - what we would lose today if the counterparty defaulted. |
| **NGR** | Net-to-gross ratio `max(net MtM, 0) / sum of positive MtMs`; measures netting benefit. |
| **PFE add-on** | `sum(notional x factor x sqrt(min(T, 1))) x (0.4 + 0.6 x NGR)`; illustrative potential future exposure. |
| **EAD estimate** | `RC + PFE add-on` (no alpha multiplier). |
| **VaR (99%, 1d)** | Loss not exceeded on 99% of the last 250 historical days, applied to today's positions. |
| **ES (99%, 1d)** | Average loss on the days at or beyond the VaR quantile. |
| **CSA** | Credit support annex: the margin agreement with a counterparty. |
| **Threshold / MTA / rounding** | Unsecured exposure allowed before collateral is due / smallest call or return that is exchanged / increment to which amounts are rounded. |
| **Break** | Any difference between the front-office trade and the back-office settlement record. |

|---|---|---|
| NFR-01 Auditability | Every rejection is explainable. | Quarantine files list failing rule ids; reconciliation separates "rejected by DQ" from genuine breaks. |
| NFR-02 Reproducibility | Same input => same output. | Seeded generator, deterministic `ingest_seq`, ordered outputs. |
| NFR-03 Maintainability | New rule = one declarative entry + one test. | `Rule` dataclass; engine evaluates all rules in a single pass. |
| NFR-04 Performance | Full run on the sample in well under a minute on a laptop. | Single-pass rule evaluation, broadcast joins for small masters, native Spark expressions (no Python UDFs). |

| NFR-06 Testability | Business logic verifiable without the full pipeline. | Risk, margin, reconciliation and rules take DataFrames as arguments; unit tests plus an end-to-end regression test. |

## 10. Assumptions, constraints and known limitations

1. Weekday-only business calendar; no market holidays. Settlement offsets are business-day counts.
2. Amounts are `double` for analytical convenience. A production ledger would use decimals.
3. All instruments are cash products priced per unit (bonds per 100 face via `price_multiplier = 0.01`).
4. One netting set per counterparty. No cross-currency collateral, no haircuts.
5. A day without a usable price contributes zero P&L for that instrument in the VaR scenarios, and the next available price produces a multi-day return. Gaps are reported by PRC_006 so they stay visible.
6. A stale collateral balance (COL_003) is a WARNING, so it still feeds the margin calculation. Treating it as blocking is a candidate change (see section 11).
7. Add-on factors are illustrative and **not** supervisory factors. Outputs must not be used for regulatory reporting.
8. Prices of instruments that are quarantined in the master are kept in staging but unused (price rule PRC_002 checks existence in the raw master to avoid double-counting the same root cause).

## 11. Open questions and candidate changes

| # | Question for the business | Impact |
|---|---|---|
| Q1 | Should a stale collateral balance block the margin call (CRITICAL) instead of warning? | Avoids calling on out-of-date balances. |
| Q2 | Which one-day move should be treated as a corporate action rather than a bad tick? | Tunes `price_spike_threshold`; may need a corporate-action feed. |
| Q3 | Should one bad instrument record reject all its trades, or park them for repair and re-processing? | Today 4 bad records (10% of the master) reject 67 trades (9.5% of the blotter). A repair queue would shorten recovery. |
| Q4 | Is the 10% trade-price tolerance right per asset class (bonds move far less than equities)? | Fewer false positives on equities, tighter control on bonds. |
| Q5 | Do we need a business-day calendar per market? | Removes false "missing price" findings on local holidays. |
